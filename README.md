# Engineer Quest

> **Build it. Explain it. Own it.**

**AIに作ってもらうのではなく、AIに鍛えてもらう。**

Engineer Quest は、実務に近い開発課題を自分で設計・実装し、AIによるレビューと技術面談を通じて、  
**「作れる・説明できる」エンジニアを育てる実践型学習プラットフォーム**です。

---

## Why Engineer Quest?

### 「作れるようになった」からこそ、「理解できること」が重要になった

以前は、新しいサービスのアイデアを思いついても、

- 技術力が足りず、実装方法が分からなくて諦める
- 途中まで作ったものの、完成させられずに終わる
- 作りたい機能を実現するまでに多くの技術を学ぶ必要がある

ということがありました。

一方で、その過程そのものが技術を学ぶ機会でもありました。

「これを作りたい。でも作り方が分からない」

という問題にぶつかり、調べ、試し、失敗しながら実装することで、
必要な技術を身につけていました。

しかし、生成AIの登場によって開発のあり方は大きく変わりました。

今では、作りたいものをAIに伝えれば、
これまで自分では実装できなかったものでも、
短期間でプロトタイプまで作れるようになっています。

「技術力が足りないから、とりあえず作ってみることすらできない」

というハードルは、以前より大幅に低くなりました。

これは非常に大きな変化です。

---

### AI時代は「コードを書く速さ」だけではなくなる

AIがコードを書けるようになるほど、
人間がコードを入力する速度そのものの重要性は相対的に下がっていきます。

その代わり、重要になると考えているのが、

- 何を作るべきか考える
- とりあえず作って試してみる
- 必要な情報を事前に整理する
- 適切な要件や制約を与える
- AIへの指示を工夫する
- AIの出力をレビューする
- 正しく動いているか検証する
- 問題があれば原因を調査する
- 最終的な品質に責任を持つ

といった能力です。

特に重要なのが、

> **AIが出力した情報やコードを、自分でチェック・検証できる能力**

だと考えています。

AIはコードを生成できます。

しかし、そのコードが、

- 本当に要件を満たしているのか
- セキュリティ上問題がないのか
- 同時アクセスでも正しく動くのか
- データを壊す可能性がないのか
- パフォーマンス上問題がないのか
- 本番環境で運用できる品質なのか

を最終的に判断する必要があります。

AIを使えば使うほど、
その出力を評価するための技術力が必要になります。

---

### エンジニアは「実装者」であると同時に「依頼者」になる

AIを使った開発では、自分自身がAIに仕事を依頼する立場にもなります。

仕事を依頼するとき、

- 何を作ってほしいのか
- どのような制約があるのか
- どの情報を事前に渡すべきなのか
- 何を完了条件とするのか
- どこまでAIに任せるのか
- 何を人間が確認するのか

を整理してから依頼することが重要になります。

これは、人に仕事を依頼するときと似ています。

相手が仕事を進めやすいように必要な情報を揃え、
曖昧な部分を減らし、
期待する結果を明確にする。

AI時代のエンジニアには、
実装する側の視点だけでなく、

> **仕事を正しく依頼し、その成果物を評価する側の視点**

も必要になると考えています。

---

### では、技術力をどこで身につけるのか？

ここで、自分自身が一つの問題を感じるようになりました。

以前は、

> **作りたいものを作りながら技術を学ぶ**

ことが、自分にとって大きな学習方法でした。

しかし今は、本当に作りたいサービスほどAIを積極的に使います。

作りたいものは単なる勉強用ではありません。

できるだけ早く完成させたい。

実際に使えるものにしたい。

品質を高くしたい。

そして、できれば自分だけではなく、
他の人にも使ってもらえるサービスにしたい。

そのため、本当に作りたいプロダクトの開発では、

> 「勉強のためにAIを使わない」

という選択をしたくありません。

AIを使って開発速度を上げ、
品質の高いものを作ることを優先したいからです。

その結果、

> **AIを使ってプロダクトを作れるようになった一方で、自分自身の技術力を鍛える場所が減っている**

と感じるようになりました。

---

### だから Engineer Quest を作る

そこで、

> **プロダクトを作る場所と、技術力を鍛える場所を分ける**

ことにしました。

本当に作りたいプロダクトでは、
AIを最大限活用して完成を目指す。

一方で Engineer Quest では、
AIに答えを作ってもらうのではなく、
実務に近い課題を自分で考え、設計し、実装する。

そしてAIには、

- Questを出題してもらう
- 必要なときだけHintをもらう
- 実装したコードをレビューしてもらう
- 問題点を指摘してもらう
- 「なぜこの実装にしたのか？」と質問してもらう
- 技術面談で理解できているか確認してもらう

という役割を持たせます。

つまり、

> **AIに作ってもらうのではなく、AIに鍛えてもらう。**

これが Engineer Quest を作ろうと思った理由です。

Engineer Quest が目指すのは、
AIを使わないエンジニアを育てることではありません。

AIを積極的に使いながらも、

**AIが作ったものを理解し、検証し、改善し、最終的に自分で責任を持てるエンジニアになること。**

そのための実践的なトレーニング環境を作ります。

---

## Philosophy

Engineer Quest の中心思想は、

> **AIに作ってもらうのではなく、AIに鍛えてもらう。**

です。

Engineer Quest では、単にコードが動けば完了とはしません。

```text
Build it.
   +
Explain it.
   ↓
Own it.
```

### Build it.

自分で調査し、設計し、実装する。

### Explain it.

なぜその技術・設計・実装を選んだのか説明する。

### Own it.

AIが生成したコードではなく、自分で理解し説明できる技術として身につける。

---

## Target

Engineer Quest は、完全なプログラミング初心者向けのサービスではありません。

主な対象は、

- 基本文法は理解している
- FrameworkやCloudの基本知識はある
- しかし実務機能を一人で完成させる自信がない
- AIを使えば作れるが、自分の実力になっているか不安
- コードは書けるが設計理由を説明するのが苦手
- 実務に近い開発経験を積みたい
- 技術面接で設計・実装について説明できるようになりたい

エンジニアです。

# Quest

Engineer Quest では、学習単位を **Quest** と呼びます。

一般的な、

```text
Reactを学ぶ
SQLを学ぶ
AWSを学ぶ
```

という技術単位の学習ではなく、

> **「実務でこのタスクを任されたとき、自分で解決できるか？」**

を重視します。

## Quest Examples

### Application

```text
アカウント登録機能を実装せよ

Googleログインを追加せよ

管理者のみアクセスできる画面を作れ

他人の予約を閲覧できないようにせよ

予約・変更・キャンセル機能を実装せよ
```

### Database / Performance

```text
二重予約を防止せよ

残り1枠への同時予約を正しく処理せよ

100万件のデータから高速検索せよ

遅いAPIの原因を調査し改善せよ

適切なIndexを設計せよ
```

### UI / UX

```text
予約フォームの離脱率を改善せよ

Loading / Error / Empty Stateを実装せよ

スマートフォンでも利用できるUIへ改善せよ
```

### Infrastructure / DevOps

```text
CI/CDを構築せよ

AWSへアプリケーションをデプロイせよ

Terraformでインフラを構築せよ

監視を導入せよ

本番障害の原因を特定せよ
```

# Live Preview

提出されたアプリケーションは、隔離されたSandbox環境でBuild・起動します。

```text
GitHub
   │
   │ Push
   ▼
Engineer Quest
   │
   ▼
Submission
   │
   ▼
┌────────────────────────┐
│ Sandbox                │
│                        │
│ Build                  │
│ Run                    │
│ Test                   │
│ MiniStack              │
└────────────┬───────────┘
             │
             ▼
        Live Preview
```

ユーザーは、自分が実装したアプリケーションをEngineer Quest上から実際に操作できます。

提出後は、

```text
Preview | Tests | AI Review | Interview
```

のように、実行結果・テスト・レビュー・面談を確認できる環境を目指します。

---

# Automated Test

提出されたコードは、Questごとに定義された自動テストによって評価します。

例えば、

> 二重予約を防止せよ

というQuestなら、

```text
User A ──┐
         ├── 同じ予約枠へ同時リクエスト
User B ──┘
              ↓
       1件だけ成功するか？
```

などを実際に検証します。

評価をすべてAIに任せるのではなく、

```text
Deterministic Test
        +
Static Analysis
        +
AI Review
        +
Technical Interview
```

を組み合わせます。

# AI Code Review

AIは提出されたコードをレビューします。

主な評価対象：

- Correctness
- Code Quality
- Maintainability
- Security
- Performance
- Architecture / Design
- Testing

単純に問題点を列挙するだけではなく、

> **「なぜこの実装にしたのか？」**

を技術面談で確認するための材料としても利用します。

# AI Technical Interview

提出したコードについて、AIとのリアルタイム技術面談を行います。

```text
AI:
なぜTransactionを使用しましたか？

User:
同時更新時の整合性を保つためです。

AI:
UNIQUE制約だけでは不十分でしょうか？

User:
...

AI:
では、残り1枠に2人が同時に予約した場合を
考えてみましょう。
```

固定された質問を順番に聞くのではなく、

- Quest
- 提出コード
- Test結果
- AI Review
- ユーザーの回答
- 過去の面談内容

をもとに、質問を動的に深掘りします。

---

# AI Hint

Engineer Quest のAIは、最初から答えを提示することを目的としません。

必要に応じて段階的なHintを提供します。

```text
Hint 1
考えるポイント
    ↓
Hint 2
関連する技術・キーワード
    ↓
Hint 3
設計の方向性
    ↓
必要な場合のみ詳細な解説
```

目的はAIに実装してもらうことではなく、

> **AIを使って、自分で考えられるようになること**

です。

# Security

Engineer Quest ではユーザーが提出したコードを実行するため、Sandboxのセキュリティを重要な要件として扱います。

想定する対策：

- Ephemeral Sandbox
- CPU Limit
- Memory Limit
- Execution Timeout
- Process Limit
- Network Restriction
- Secret Isolation
- Rate Limit
- Secret Scanning
- Least Privilege
- Sandbox破棄

```text
Submission
    ↓
Ephemeral Sandbox
    ↓
Build / Run / Test
    ↓
Result
    ↓
Destroy
```

ユーザーコードを通常のアプリケーションサーバー上で直接実行しない設計を目指します。

# Development Principles

Engineer Quest の開発では以下を重視します。

### 1. Build it. Explain it. Own it.

サービス自身の開発でも、技術を採用する理由を説明できるようにします。

### 2. Local First AI

可能な部分ではローカルAIを活用し、AI基盤そのものも開発対象とします。

### 3. Measure Performance

特にリアルタイム音声処理では、感覚ではなくLatencyを計測します。

```text
End of Speech
STT Final
LLM First Token
TTS First Audio
TTFA
```

### 4. Security by Design

ユーザーコードを実行するサービスであるため、Sandbox・権限制御・ネットワーク分離を後付けにしません。

### 5. Infrastructure as Code

InfrastructureはTerraform等で再現可能にします。
